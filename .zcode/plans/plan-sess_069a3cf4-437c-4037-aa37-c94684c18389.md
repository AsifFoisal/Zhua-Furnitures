## Context

Checkout in South Africa fails with HTTP 500 at the payment step. The PayFast flow is: `/api/orders` → `/api/payments/payfast/initiate` → browser POSTs the returned form to PayFast. The initiation route never calls PayFast, so a 500 can come from either our site or PayFast's process page.

I traced both sides. There are real defects in our code, and one production-only configuration trap that is the most likely cause of a PayFast-hosted 500:

- **Build-time mode**: `NEXT_PUBLIC_PAYFAST_MODE` is inlined at build (`src/lib/supabase/env.ts:23,42-48`). A deployment built without it silently uses **sandbox** while the server holds **live** merchant credentials — PayFast then fails on the posted payment. Mixing sandbox/live credentials is a known cause of the PayFast process-page 500.
- **Bare 500s**: `/api/payments/payfast/initiate` has no error boundary. A null JSON body (`route.ts:72`), an invalid forwarded origin (`route.ts:35`, `site-url.ts:56-60`), or Supabase client creation can throw an uncaught exception. Its only explicit 500 is the order UPDATE (`route.ts:150-166`) returning raw DB text.
- **Form/signature mismatch risk**: empty values are dropped from the signature (`payfast.ts:25-31`) but still posted as empty inputs (`checkout/page.tsx:254-264`). PayFast requires empty fields to be omitted; a single-word name makes `name_last` empty.
- **Confirmed webhook 500**: quote payments set a quote UUID as `payment_webhook_events.related_order_id`, which FKs to `orders` (`webhook/route.ts:131`, `migrations/20260406_0007:75`) → FK violation → 500 on every quote ITN. The quote branch also reads `payload.amount` instead of `amount_gross` (`webhook/route.ts:165`).
- **Masked errors**: both checkout clients call `res.json()` before checking status, so an HTML 500 becomes "Unexpected token '<'".

Intended outcome: PayFast mode is resolved correctly at runtime, the initiation route never returns an unexplained 500, the posted form exactly matches the signed fields, and the confirmed webhook 500 is fixed.

## Changes

1. **`src/lib/supabase/env.ts`** — resolve mode from server `PAYFAST_MODE` first, then `NEXT_PUBLIC_PAYFAST_MODE`. In production, if neither is set, stop with a clear "PayFast mode is not configured" 503 instead of silently using sandbox. Warn when the two values disagree. In live mode validate that return/cancel/notify URLs are absolute and `https`, so a bad URL fails with an actionable message rather than at PayFast.

2. **`src/lib/payments/payfast.ts`** — add `buildPayFastFields()` returning only non-empty fields in insertion order, and guarantee non-empty `name_first`/`name_last`. Keep the existing signature algorithm unchanged (order-preserving, PHP-style urlencode, passphrase last).

3. **`src/app/api/payments/payfast/initiate/route.ts`** — validate the body is a non-null object with a UUID; build callback URLs only through a helper that cannot throw; wrap Supabase lookup/update in try/catch; map missing-column/table/constraint errors to a clear 503 ("payment schema is out of date") and other DB failures to a sanitized 500; log `mode`, `stage`, `orderId`, and the DB error code (never raw messages or secrets to the client). Use `buildPayFastFields()` for the response.

4. **`src/lib/supabase/errors.ts`** (new, small) — `isSchemaDriftError(error)` for codes `42P01`, `42703`, `42883`, `23514`, reused by the initiate and orders routes so a missing migration is reported as configuration, not as an opaque 500.

5. **`src/app/api/orders/route.ts`** — use the helper on the product/zone/order/order-item failures so schema drift produces a clear message and a logged code instead of a raw Postgres string.

6. **`src/app/checkout/page.tsx`** and **`src/app/quote-payment/actions.tsx`** — add a `readJsonResponse()` helper (reads text, parses JSON when possible, falls back to `HTTP <status>`) for both fetches, so the real failure is shown.

7. **`src/app/api/webhooks/payfast/route.ts`** and **`src/lib/quote-payments.ts`** — insert webhook events with `related_order_id: null` until the reference is confirmed to be an order, then set it; read `amount_gross` (fallback `amount`) for quotes; remove the `expectedCents / 100` tolerance that would accept a 100× smaller payment.

## Deployment step (required, outside code)

Set `PAYFAST_MODE=live` (or the correct sandbox value) in the production environment and confirm `PAYFAST_MERCHANT_ID`/`PAYFAST_MERCHANT_KEY` belong to the same mode. Also confirm migrations `0007`, `0008`, and `0013` are applied to the production Supabase project — without `0007`, order creation fails with a check-constraint 500.

## Verification

- `npx tsc --noEmit` and `npm run lint`.
- Run `npm run dev` and probe the initiation route: invalid body → 400, unknown order → 404, missing config → 503 with an actionable message; no uncaught stack traces.
- Unit-check the signature/form helper (field order preserved, empties omitted, MD5 deterministic) without network calls.
- One end-to-end sandbox transaction only if sandbox credentials are available — no live payment will be initiated.
- Replay a quote-shaped webhook payload against a test DB to confirm the event inserts with a null `related_order_id` instead of failing the FK. If no safe test DB exists, verify by code review and log inspection.
